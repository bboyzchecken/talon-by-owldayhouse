# ระบบเอกสารขาย รายรับ-รายจ่าย และภาษี (แทน PEAK สำหรับงานประจำวัน)

สถานะ: **ขั้น 1–8 เสร็จ** (ตาราง ตัวออกเลข API หน้าจอ ทะเบียน รับเงิน รายจ่าย ภาษีรายเดือน ภาพรวมการเงินและไฟล์ส่งสำนักบัญชี) · งานกับสำนักบัญชี (ขอ 50 ทวิ, ส่งข้อมูลภาษี, QR) ดู `accounting-handoff.md` · ถัดไป: ต่อ PEAK ทาง API เมื่อมีแพ็กเกจ · ปรับ 16 พ.ย. 2026: เพิ่มฝั่งรายจ่าย ภาษีรายเดือน
และหัก ณ ที่จ่ายทั้งสองทาง ตามที่บริษัทขอ (ดู "การตัดสินใจจากบริษัท")

เอกสารนี้อยู่คนละที่กับ `docs/design-system/` เพราะนั่นเป็นเรื่องหน้าตาของเว็บการตลาด
ส่วนนี่เป็นเครื่องมือภายใน แผนของเครื่องมือภายในอื่น ๆ ให้มาอยู่โฟลเดอร์นี้ด้วย

## โจทย์

ทุกวันนี้ออกเอกสารด้วย `owl-docs` ซึ่งทำงานได้ดีในส่วนของ "หน้าตาเอกสาร" แต่ไม่มี 4 อย่าง

1. เลขที่เอกสารรันอัตโนมัติ
2. ฐานข้อมูลลูกค้าที่ไม่ต้องกรอกซ้ำ
3. ประวัติว่าใครออกเอกสารอะไรเมื่อไหร่
4. ภาพรวมรายได้

และบริษัทต้องการเห็นอีก 3 เรื่องในที่เดียว

5. รายจ่าย พร้อมภาษีซื้อที่เอามาหักได้
6. VAT ของแต่ละเดือน: ภาษีขาย − ภาษีซื้อ = ต้องจ่ายเท่าไหร่ จ่ายแล้วหรือยัง
7. หัก ณ ที่จ่าย ทั้งสองทาง: ลูกค้าหักเรา (ได้หนังสือรับรองมาหรือยัง)
   และเราหักผู้รับจ้าง (นำส่งสรรพากรหรือยัง ส่งหนังสือรับรองให้เขาหรือยัง)

ทุกอย่างที่เป็น "จ่ายแล้ว / ได้รับแล้ว / ส่งแล้ว" มีปุ่มกดพร้อมแนบหลักฐาน

เป้าหมายคือ **ไม่ใช่โปรแกรมบัญชีเต็มรูป** แต่เป็นสิ่งที่ใช้จริงทุกวัน และตอบได้ทุกเดือนว่า
เงินเข้าเท่าไหร่ ออกเท่าไหร่ ภาษีต้องจ่ายเท่าไหร่ และอะไรยังค้างอยู่

## ของเดิมที่เก็บไว้

`apps/web/lib/owl-docs/template.html` (995 บรรทัด) ทำได้แล้วและห้ามทำใหม่:

- 3 ประเภท: ใบเสนอราคา · ใบแจ้งหนี้ · ใบเสร็จรับเงิน/ใบกำกับภาษี
- VAT 3 โหมด (แยก / รวม / ไม่มี), หัก ณ ที่จ่าย, โหมดออกในนามบุคคลธรรมดา
- แปลงจำนวนเงินเป็นตัวหนังสือไทย, แบ่งหน้าอัตโนมัติตอนพิมพ์, ป้ายต้นฉบับ/สำเนา
- ร่างอีเมลส่งลูกค้า — **เป็นปุ่มร่างเท่านั้น** ระบบเติมหัวเรื่องกับเนื้อความให้ แล้วคัดลอก
  หรือเปิดโปรแกรมอีเมลในเครื่องผ่าน `mailto:` คนกดส่งเองข้างนอก ระบบไม่ส่งอีเมลเอง
  (กฎ "ไม่มีอีเมลในระบบ" ใน CLAUDE.md) กดร่างแล้วลง log ว่า "ร่างอีเมล" ไม่ใช่ "ส่งแล้ว"
  คนกด "ส่งให้ลูกค้าแล้ว" เองเมื่อส่งจริง

เอาเทมเพลตนี้ไป render จากข้อมูลใน DB แทนการกรอกมือ

**จุดอ่อนที่การย้ายครั้งนี้แก้ไปในตัว:** หน้า `/owl-docs/` ป้องกันด้วยรหัสผ่านฝั่ง browser
ซึ่งโค้ดเองเขียนคอมเมนต์ยอมรับว่าเป็นการบังตา ไม่ใช่ auth จริง ตอนนี้ข้อมูลลูกค้าและราคา
อยู่บนเว็บ public ย้ายเข้า CRM แล้วได้ login จริงกับ role จริง

## บทเรียนจาก PEAK Open API

ยังไม่ต่อ API เขาในรอบแรก แต่**ออกแบบให้ต่อได้โดยไม่ต้องรื้อตาราง** เพราะสำนักบัญชีของบริษัท
ใช้ PEAK และบริษัทต้องต่ออายุ PEAK อยู่แล้ว (ดู "ต่อกับ PEAK" ด้านล่างสำหรับการเทียบฟิลด์)

โครงสร้าง 4 อย่างที่ลอกมา

| สิ่งที่ PEAK ทำ | เอามาใช้อย่างไร |
| --- | --- |
| `createbyquotation` / `createbyinvoice` | เอกสารสร้างต่อจากกันเป็นสาย ลอกลูกค้าและรายการมาให้ |
| มี `approve` กับ `void` ไม่มี delete | เอกสารที่ออกแล้วยกเลิกได้ ลบไม่ได้ เลขไม่หาย |
| `contacts` และ `products` เป็นทะเบียนแยก | ทะเบียนผู้ติดต่อ (ลูกค้าและผู้ขาย) และทะเบียนรายการขาย |
| `paidpayment` แยกจากใบแจ้งหนี้ | การรับเงินเป็นรายการของตัวเอง ทำให้รู้ยอดค้างรับ |

## ต่อกับ PEAK

อ่านจาก PEAK Open API v1.0.2 (`developers.peakaccount.com`, 16 พ.ย. 2026)

### ตอนนี้กับวันหน้า

| ช่วง | วิธี | เหตุผล |
| --- | --- | --- |
| ตอนนี้ | สำนักบัญชี**คีย์มือ**จากเอกสารที่เราส่ง → ระบบเรามี export รายเดือนที่เรียงตามช่องของ PEAK | ต่อ API ต้องใช้แพ็กเกจ Pro Plus ขึ้นไปและยื่นขอสิทธิ์ |
| วันหน้า | ส่งเข้า PEAK ทาง API ทางเดียว (เรา → PEAK) ผ่านตัวแปลง `apps/api/pkg/peak` | ตารางมีช่องและรหัสครบแล้ว เพิ่มแค่ตัวแปลง |

**เลขเอกสารเป็นของระบบเรา** ทุก endpoint สร้างเอกสารของ PEAK รับ `code` และใช้เลขที่ส่งไป
(ไม่ส่งจึงออกเลขเอง) เราจึงส่งเลข `QO-2611-001` ไปเป็น `code` ใบกำกับภาษีมีเลขชุดเดียวทั้งสองระบบ

### หลักการตั้งชื่อ

1. **ชื่อคอลัมน์เป็นของเรา** (snake_case ตาม `PROJECT_TEMPLATE.md`) แต่**ความหมายและค่า enum ตรงกับ PEAK หนึ่งต่อหนึ่ง**
   ตัวแปลงจึงแค่เปลี่ยนชื่อและรูปวันที่ ไม่ต้องเดาความหมาย
2. ค่าที่เป็นตัวเลขของ PEAK (ประเภทผู้ติดต่อ, ประเภท VAT) **เก็บเป็นค่าเดียวกับ PEAK** แล้วใส่ป้ายไทยในหน้าจอ
3. ทุกตารางที่ส่งไป PEAK ได้ มี `peak_id`, `peak_synced_at`, `peak_sync_error` (ว่างไว้จนกว่าจะต่อ)
4. วันที่เก็บเป็น `date` ตัวแปลงแปลงเป็น `yyyyMMdd` ตอนส่ง เงินเก็บ `numeric(14,2)`

### VAT: เก็บแบบ PEAK คือ "หัวเอกสาร + รายบรรทัด"

| ที่ | ของเรา | PEAK | ค่า |
| --- | --- | --- | --- |
| หัวเอกสาร | `tax_status` | `taxStatus` | 0 ราคาไม่รวม VAT · 1 ราคารวม VAT |

3 โหมดเดิมของ owl-docs แปลงได้ตรง ๆ: แยก = 0 + 3 · รวม = 1 + 3 · ไม่มี = 0 + 1

### ไฟล์หลักฐาน

PEAK มี `insertfile` ของใบเสนอราคา ใบแจ้งหนี้ ใบเสร็จ และรายจ่าย ไฟล์ของเราอยู่ R2 อยู่แล้ว
ตัวแปลงส่งต่อได้ภายหลัง

### ของเราเท่านั้น (PEAK API ไม่มี endpoint)

- สถานะหนังสือรับรองหัก ณ ที่จ่าย (50 ทวิ) ที่ลูกค้าต้องส่งให้เรา และที่เราต้องส่งให้ผู้รับจ้าง
- `tax_filings`: ภ.พ.30, ภ.ง.ด.3/53 ยอดที่ล็อกและหลักฐานการจ่าย
- การผูกกับ `leads`, เซลส์ที่ดูแล, utm

ส่วนนี้สำนักบัญชีดูใน PEAK ได้จากรายงานของ PEAK เอง เราเก็บไว้เพื่อตามงานและเก็บหลักฐาน

### ตอนต่อจริง

- PEAK มี endpoint แบบคิว (`.../queue`) และ webhook ตัวแปลงควรส่งเข้าคิวแล้วรอผล ไม่รอสด
- ส่ง `Approve` เฉพาะเอกสารที่ออกเลขแล้ว ร่างของเราไม่ส่ง
- ตรวจเรื่อง `taxStatus` = 2 ซึ่ง schema ยอมให้ส่งแต่ตารางค่าไม่ได้อธิบาย ก่อนใช้

| `billing_contacts` | ลูกค้าและผู้ขายในทะเบียนเดียว (แบบ PEAK) ชื่อ ประเภท เลขผู้เสียภาษี สาขา ที่อยู่แยกช่อง ผู้ติดต่อ — ผูกกับ `leads.id` ได้ (null ได้) ลูกค้าหนึ่งรายมีได้หลายแถว |
| `products` | รายการที่ขายบ่อย: รหัส ชื่อ หน่วย ราคาตั้งต้น ประเภท VAT ผูกกับ `interest` ทั้ง 6 บริการ |

| `document_items` | บรรทัดรายการของเอกสาร พร้อม `vat_type` และหัก ณ ที่จ่ายรายบรรทัด |
| `document_numberings` | รูปแบบเลขต่อประเภท: ตัวย่อ รีเซ็ต จำนวนหลัก |
| `document_counters` | ตัวนับเลข หนึ่งแถวต่อ (ประเภท, งวด) |
| `document_events` | log: สร้าง / ออกเลข / ร่างอีเมล / ส่งให้ลูกค้าแล้ว / ยกเลิก / บันทึกรับเงิน |
| `payments` | การรับเงิน (ฝั่งขาย) และการจ่ายเงิน (รายจ่าย) ของเอกสาร รวมยอดหัก ณ ที่จ่าย และสถานะหนังสือรับรอง |
| `tax_filings` | ภาษีที่ต้องนำส่งของแต่ละงวด: ภ.พ.30, ภ.ง.ด.3, ภ.ง.ด.53 พร้อมยอดที่ล็อกไว้ตอนจ่าย และหลักฐาน |

หลักฐานทุกชิ้น (สลิปโอน ใบกำกับภาษีของผู้ขาย หนังสือรับรองหัก ณ ที่จ่าย ใบเสร็จสรรพากร)
ใช้ตาราง `files` กลางที่มีอยู่แล้ว ซึ่งผูกกับระเบียนประเภทไหนก็ได้ (`owner_type`, `owner_id`)
เพิ่มแค่ค่า `owner_type` ใหม่ (`document`, `payment`, `tax_filing`) ไฟล์อยู่บน R2 แบบ private เหมือนเดิม

**เงินเป็น `decimal` ไม่ใช่ float** (`numeric(14,2)` ผ่าน `shopspring/decimal`) เอกสารภาษีต้องตรงทุกสตางค์

**ยอดเงินเก็บเป็นค่าที่คำนวณแล้ว ไม่คำนวณใหม่ตอนอ่าน** เพราะเอกสารภาษีต้องแสดงสิ่งที่พิมพ์ออกไป
ตลอดไป ต่อให้อัตรา VAT หรือราคาตั้งต้นเปลี่ยนทีหลัง

## เลขที่เอกสาร

รูปแบบ `QO-20261100001` = ตัวย่อ-ปีเดือน(ค.ศ.)-ลำดับ 5 หลัก เป็นรูปแบบตั้งต้นของ PEAK
และเป็นแบบที่ owl-docs พิมพ์อยู่แล้ว (`QO-…`, `IV-…`, `RT-…`) ตั้งค่าได้ต่อประเภทเอกสาร
ในตาราง `document_numberings`: ตัวย่อ รีเซ็ตรายเดือนหรือรายปี และจำนวนหลัก

ตัวย่อตั้งต้น: QO ใบเสนอราคา · IV ใบแจ้งหนี้ · RT ใบเสร็จ/ใบกำกับภาษี · TX ใบกำกับภาษี · CN ใบลดหนี้ ·
BN ใบวางบิล · DN ใบเพิ่มหนี้ · EXP รายจ่าย (QO IV RT มาจาก owl-docs ที่เหลือรอบริษัทยืนยัน)

เริ่มต่อจากเลขที่บริษัทใช้ไปแล้ว: `odh-internal-api set-doc-number -type 101 -period 202611 -next 42 -by admin`
(ใบถัดไปได้ `QO-20261100042`) ระบบไม่ยอมให้ตั้งย้อนหลังต่ำกว่าเลขที่ออกไปแล้ว และลงประวัติทุกครั้ง

กติกา 4 ข้อที่ห้ามพลาด:

1. **จองเลขตอนกด "ออกเอกสาร" ไม่ใช่ตอนสร้างร่าง** ร่างที่ทิ้งไว้จะได้ไม่กินเลข
2. **จองใน transaction เดียวกับการบันทึก** ด้วย `UPDATE document_counters SET next_value = next_value + 1 ... RETURNING next_value` แถวนั้นถูกล็อกระหว่าง transaction สองคนกดพร้อมกันจึงชนกันไม่ได้
3. **ยกเลิกแล้วเลขยังอยู่** ติดป้ายยกเลิกไว้ ไม่ลบ ไม่เอาเลขกลับมาใช้ซ้ำ — ใบกำกับภาษีมีเลขหายไม่ได้
4. **เอกสารที่ออกแล้วแก้ไม่ได้** ต้องยกเลิกแล้วออกใหม่ ก่อนออกเลขแก้ได้อิสระ

ต้องมีเทสต์ที่ยิงขอเลขพร้อมกันหลาย goroutine แล้วยืนยันว่าไม่มีเลขซ้ำและไม่มีเลขข้าม
— มีแล้วที่ `apps/api/pkg/docnumber/docnumber_test.go`: 60 คนออกพร้อมกัน 1 ใน 4 บันทึกไม่สำเร็จ
เลขที่ได้ต้องเรียง 1..45 ไม่ซ้ำไม่ข้าม ฐานข้อมูลกันซ้ำอีกชั้นด้วย unique index ต่อประเภท และ
check ว่าร่างต้องไม่มีเลข เอกสารที่ออกแล้วต้องมีเลข

## สถานะและสายเอกสาร

```
ร่าง ──ออกเอกสาร──► ออกแล้ว ──ยกเลิก──► ยกเลิกแล้ว
                        │
ใบเสนอราคา ──สร้างต่อ──► ใบแจ้งหนี้ ──สร้างต่อ──► ใบเสร็จ/ใบกำกับภาษี
```

## รายรับ

ใบแจ้งหนี้หนึ่งใบรับเงินได้หลายครั้ง (มัดจำ งวด) แต่ละครั้งเป็นแถวใน `payments`

| ช่อง | หมายเหตุ |
| --- | --- |
| วันที่ได้รับ · ยอดที่โอนเข้าจริง | |
| ยอดที่ลูกค้าหัก ณ ที่จ่าย · อัตรา | ปกติงานบริการ 3% ของยอดก่อน VAT ระบบเสนอให้ แก้ได้ |
| สลิป/หลักฐานการรับเงิน | แนบตอนกด "ได้รับเงินแล้ว" |
| หนังสือรับรองหัก ณ ที่จ่าย (50 ทวิ) | สถานะ `รอ` → `ได้รับแล้ว` กดพร้อมแนบไฟล์ |

ยอดที่โอนเข้า + ยอดที่ถูกหัก = ยอดที่เก็บได้ของใบนั้น ระบบจึงรู้ว่าใบไหนจ่ายครบ ใบไหนค้าง

**หนังสือรับรองที่ยังไม่ได้คืนมาคือเงิน** เพราะยอดที่ถูกหักใช้เป็นเครดิตภาษีเงินได้ตอนสิ้นปีได้
ก็ต่อเมื่อมีหนังสือรับรอง จึงมีรายการ "รอหนังสือรับรองจากลูกค้า" แยกให้เห็น พร้อมยอดรวม

**ภาษีขายของงานบริการเกิดเมื่อได้รับเงิน** บริษัทยืนยันว่าออกใบเสร็จ/ใบกำกับภาษีหลังได้รับเงินจริงเสมอ
ใบนี้จึงออกตอนกด "ได้รับเงินแล้ว" และ VAT ของเดือนนับจากใบกำกับภาษีที่ออกในเดือนนั้น

## ภาษีรายเดือน (`tax_filings`)

หนึ่งแถวต่อ (แบบ, งวด) ระบบคำนวณยอดจากเอกสาร คนกด "จ่ายแล้ว" พร้อมแนบใบเสร็จของสรรพากร

| แบบ | ยอด | กำหนดตามปกติ |
| --- | --- | --- |
| ภ.พ.30 | ภาษีขาย − ภาษีซื้อ ของเดือน ถ้าติดลบคือเครดิตยกไปเดือนหน้า | วันที่ 15 ของเดือนถัดไป (ยื่นออนไลน์ได้ช้ากว่า) |
| ภ.ง.ด.53 | ยอดที่เราหักนิติบุคคลในเดือน | วันที่ 7 ของเดือนถัดไป (ยื่นออนไลน์ได้ช้ากว่า) |
| ภ.ง.ด.3 | ยอดที่เราหักบุคคลธรรมดาในเดือน | วันที่ 7 ของเดือนถัดไป (ยื่นออนไลน์ได้ช้ากว่า) |

กติกา:

1. **ยอดที่จ่ายถูกล็อกไว้ในแถว** ตอนกด "จ่ายแล้ว" ถ้ามีคนแก้รายจ่ายหรือยกเลิกเอกสารของงวดนั้นทีหลัง
   ระบบไม่เปลี่ยนตัวเลขที่จ่ายไปแล้ว แต่ขึ้นป้าย "ยอดคำนวณใหม่ไม่ตรงกับที่ยื่น" ให้นักบัญชีดู
   (อาจต้องยื่นเพิ่มเติม) — ไม่แก้ย้อนหลังเงียบ ๆ
2. **งวดที่จ่ายแล้วแก้รายการในงวดไม่ได้โดยไม่ตั้งใจ** ต้องกดยืนยันและลง log ว่าใครแก้
3. **กำหนดยื่นขึ้นในปฏิทินกลางและหน้า "วันนี้" ของแอดมิน** ตั้งแต่ 5 วันก่อนครบ
4. ระบบไม่ยื่นแบบและไม่จ่ายภาษีเอง นักบัญชีหรือแอดมินยื่นที่เว็บสรรพากร แล้วกลับมากด "จ่ายแล้ว"

## รับเงินขั้น 5

- **บันทึกรับเงินได้ที่หน้าใบเสนอราคา ใบแจ้งหนี้ หรือใบวางบิลที่ออกเลขแล้ว (แอดมิน)** ใส่ยอดเงินเข้าจริงกับยอดที่ลูกค้าหัก ณ ที่จ่าย
  สองยอดรวมกันคือยอดที่ตัดออกจากเอกสาร รับเกินยอดค้างไม่ได้ และสองคนบันทึกพร้อมกันก็เกินไม่ได้ เพราะเอกสารถูกล็อกระหว่างบันทึก
- **ใบเสร็จ/ใบกำกับภาษีออกพร้อมการบันทึกรับเงิน** ใน transaction เดียวกัน ลงวันที่ตามวันที่ได้รับเงิน ภาษีขายจึงตกเดือนที่ได้รับเงินจริง
  สร้างใบเสร็จด้วยมือหรือสร้างต่อจากใบแจ้งหนี้ไม่ได้แล้ว ถ้าข้อมูลภาษีของลูกค้ายังไม่ครบ บันทึกรับเงินโดยยังไม่ออกใบเสร็จได้ แล้วกดออกใบเสร็จทีหลัง
- **VAT ตามเงิน** (`docmath.SplitPayment`) งวดย่อยได้ VAT ตามสัดส่วนปัดเป็นสตางค์ งวดที่ปิดยอดได้ VAT ที่เหลือพอดี
  ใบเสร็จทุกงวดของเอกสารเดียวกันจึงรวมกันได้เท่า VAT ของเอกสารทุกสตางค์ เอกสารที่มีทั้งบรรทัดมี VAT และไม่มี VAT ใบเสร็จแยกสองบรรทัดให้
- **หลักฐาน** สลิป (`owner_type=payment`) และหนังสือรับรอง 50 ทวิ (`payment_wht`) แนบผ่านระบบไฟล์กลาง เปิดได้เฉพาะแอดมิน
  กด "ได้รับหนังสือรับรองแล้ว" ได้เมื่อแนบไฟล์หนังสือรับรองแล้วเท่านั้น สลิปไม่นับเป็นหนังสือรับรอง
- **หน้า `/docs/payments`** แท็บ "รอหนังสือรับรอง 50 ทวิ" พร้อมยอดรวม และรายการรับเงินรายเดือน
- **ยกเลิกการรับเงิน** ต้องมีเหตุผล ใบเสร็จของรายการนั้นถูกยกเลิกด้วย (เลขที่ยังอยู่) ยอดกลับมาค้างรับ

เข้าสรรพากร — นักบัญชียังทำหน้าที่เดิม ระบบทำให้เขาได้ตัวเลขกับหลักฐานครบในที่เดียว

## การตัดสินใจจากบริษัท (16 พ.ย. 2026)

1. **อีเมลเป็นปุ่มร่าง** คนส่งเองข้างนอก ระบบไม่ส่ง
2. **บริษัทจด VAT และออกใบกำกับภาษีได้** ค่าตั้งต้น VAT แยก 7% สำนักงานใหญ่ ตาม owl-docs
3. **ต้องมีรายรับ** ได้เท่าไหร่ VAT รอจ่ายเท่าไหร่ ถูกหัก ณ ที่จ่ายเท่าไหร่ ปุ่มจ่ายแล้ว/ได้รับแล้วพร้อมแนบหลักฐาน
4. **ต้องมีรายจ่าย** VAT เท่าไหร่ หักลบกับภาษีขายแล้วเหลือจ่ายเท่าไหร่ หัก ณ ที่จ่ายนำส่งหรือยัง
   ส่งหนังสือรับรองให้อีกฝ่ายหรือยัง และหนังสือรับรองที่ลูกค้าต้องส่งให้เรา ได้รับหรือยัง
5. **เลขเอกสารเป็นของระบบเรา** ส่งไป PEAK เป็น `code`
6. **ใบเสร็จ/ใบกำกับภาษีออกหลังได้รับเงินจริงเสมอ**
7. **สำนักบัญชีคีย์มือเข้า PEAK อยู่ตอนนี้** — รอบแรกทำ export ตามช่องของ PEAK ส่วน API ทำภายหลัง
   แต่ตารางออกแบบตาม PEAK ตั้งแต่วันแรก

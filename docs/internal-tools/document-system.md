# ระบบเอกสารขาย รายรับ-รายจ่าย และภาษี (แทน PEAK สำหรับงานประจำวัน)

สถานะ: **ออกแบบแล้ว รอเริ่มเขียน** · ปรับ 16 พ.ย. 2026: เพิ่มฝั่งรายจ่าย ภาษีรายเดือน
และหัก ณ ที่จ่ายทั้งสองทาง ตามที่บริษัทขอ (ดู "การตัดสินใจจากบริษัท")

เอกสารนี้อยู่คนละที่กับ `docs/design-system/` เพราะนั่นเป็นเรื่องหน้าตาของเว็บการตลาด
ส่วนนี่เป็นเครื่องมือภายใน แผนของเครื่องมือภายในอื่น ๆ ให้มาอยู่โฟลเดอร์นี้ด้วย

## โจทย์

ทุกวันนี้ออกเอกสารด้วย `owl-docs` ซึ่งทำงานได้ดีในส่วนของ "หน้าตาเอกสาร" แต่ไม่มี 4 อย่าง

1. เลขที่เอกสารรันอัตโนมัติ
2. ฐานข้อมูลลูกค้าที่ไม่ต้องกรอกซ้ำ
3. ประวัติว่าใครออกเอกสารอะไรเมื่อไหร่
4. ภาพรวมรายได้

และบริษัทต้องการเห็นอีก 3 เรื่องในที่เดียว

5. รายจ่าย พร้อมภาษีซื้อที่เอามาหักได้
6. VAT ของแต่ละเดือน: ภาษีขาย − ภาษีซื้อ = ต้องจ่ายเท่าไหร่ จ่ายแล้วหรือยัง
7. หัก ณ ที่จ่าย ทั้งสองทาง: ลูกค้าหักเรา (ได้หนังสือรับรองมาหรือยัง)
   และเราหักผู้รับจ้าง (นำส่งสรรพากรหรือยัง ส่งหนังสือรับรองให้เขาหรือยัง)

ทุกอย่างที่เป็น "จ่ายแล้ว / ได้รับแล้ว / ส่งแล้ว" มีปุ่มกดพร้อมแนบหลักฐาน

เป้าหมายคือ **ไม่ใช่โปรแกรมบัญชีเต็มรูป** แต่เป็นสิ่งที่ใช้จริงทุกวัน และตอบได้ทุกเดือนว่า
เงินเข้าเท่าไหร่ ออกเท่าไหร่ ภาษีต้องจ่ายเท่าไหร่ และอะไรยังค้างอยู่

## ของเดิมที่เก็บไว้

`apps/web/lib/owl-docs/template.html` (995 บรรทัด) ทำได้แล้วและห้ามทำใหม่:

- 3 ประเภท: ใบเสนอราคา · ใบแจ้งหนี้ · ใบเสร็จรับเงิน/ใบกำกับภาษี
- VAT 3 โหมด (แยก / รวม / ไม่มี), หัก ณ ที่จ่าย, โหมดออกในนามบุคคลธรรมดา
- แปลงจำนวนเงินเป็นตัวหนังสือไทย, แบ่งหน้าอัตโนมัติตอนพิมพ์, ป้ายต้นฉบับ/สำเนา
- ร่างอีเมลส่งลูกค้า — **เป็นปุ่มร่างเท่านั้น** ระบบเติมหัวเรื่องกับเนื้อความให้ แล้วคัดลอก
  หรือเปิดโปรแกรมอีเมลในเครื่องผ่าน `mailto:` คนกดส่งเองข้างนอก ระบบไม่ส่งอีเมลเอง
  (กฎ "ไม่มีอีเมลในระบบ" ใน CLAUDE.md) กดร่างแล้วลง log ว่า "ร่างอีเมล" ไม่ใช่ "ส่งแล้ว"
  คนกด "ส่งให้ลูกค้าแล้ว" เองเมื่อส่งจริง

เอาเทมเพลตนี้ไป render จากข้อมูลใน DB แทนการกรอกมือ

**จุดอ่อนที่การย้ายครั้งนี้แก้ไปในตัว:** หน้า `/owl-docs/` ป้องกันด้วยรหัสผ่านฝั่ง browser
ซึ่งโค้ดเองเขียนคอมเมนต์ยอมรับว่าเป็นการบังตา ไม่ใช่ auth จริง ตอนนี้ข้อมูลลูกค้าและราคา
อยู่บนเว็บ public ย้ายเข้า CRM แล้วได้ login จริงกับ role จริง

## บทเรียนจาก PEAK Open API

ไม่ได้ต่อ API เขา แต่ลอกโครงสร้าง 4 อย่างที่เขาออกแบบไว้ดี

| สิ่งที่ PEAK ทำ | เอามาใช้อย่างไร |
| --- | --- |
| `createbyquotation` / `createbyinvoice` | เอกสารสร้างต่อจากกันเป็นสาย ลอกลูกค้าและรายการมาให้ |
| มี `approve` กับ `void` ไม่มี delete | เอกสารที่ออกแล้วยกเลิกได้ ลบไม่ได้ เลขไม่หาย |
| `contacts` และ `products` เป็นทะเบียนแยก | ทะเบียนโปรไฟล์ออกบิล และทะเบียนรายการขาย |
| `paidpayment` แยกจากใบแจ้งหนี้ | การรับเงินเป็นรายการของตัวเอง ทำให้รู้ยอดค้างรับ |

## ที่อยู่ของระบบ

เครื่องมือใหม่ใน `apps/internal` ตามสูตรใน `apps/api/README.md`:
route prefix `/api/docs/...`, โฟลเดอร์หน้าใน `apps/internal/app/docs/`, และหนึ่ง entry
ใน `apps/internal/lib/tools.ts` — auth, บัญชีผู้ใช้ และไฟล์ ใช้ของกลางที่มีอยู่แล้ว

## ตาราง

| ตาราง | เก็บอะไร |
| --- | --- |
| `billing_profiles` | ชื่อนิติบุคคล เลขผู้เสียภาษี สาขา ที่อยู่ออกบิล ผู้ติดต่อ — ผูกกับ `leads.id` ได้ (null ได้ สำหรับลูกค้าที่ไม่ได้อยู่ใน CRM) ลูกค้าหนึ่งรายมีได้หลายโปรไฟล์ |
| `service_items` | รายการที่ขายบ่อย: รหัส ชื่อ หน่วย ราคาตั้งต้น ผูกกับ `interest` ทั้ง 6 บริการ |
| `documents` | หัวเอกสาร: ประเภท เลขที่ สถานะ ลูกค้า วันที่ โหมด VAT ยอดรวมที่คำนวณแล้ว และ `source_document_id` สำหรับสายเอกสาร |
| `document_items` | บรรทัดรายการของเอกสารนั้น |
| `document_counters` | ตัวนับเลข หนึ่งแถวต่อ (ประเภท, งวด) |
| `document_events` | log: สร้าง / ออกเลข / ร่างอีเมล / ส่งให้ลูกค้าแล้ว / ยกเลิก / บันทึกรับเงิน |
| `payments` | การรับเงินของใบแจ้งหนี้ รวมยอดที่ลูกค้าหัก ณ ที่จ่าย และสถานะหนังสือรับรองที่ต้องได้คืนมา |
| `vendors` | ทะเบียนผู้ขาย/ผู้รับจ้าง: ชื่อ เลขผู้เสียภาษี สาขา ที่อยู่ เป็นบุคคลหรือนิติบุคคล (กำหนดว่าหักแล้วยื่น ภ.ง.ด.3 หรือ 53) |
| `expenses` | รายจ่ายหนึ่งรายการ ดูหัวข้อ "รายจ่าย" |
| `tax_filings` | ภาษีที่ต้องนำส่งของแต่ละงวด: ภ.พ.30, ภ.ง.ด.3, ภ.ง.ด.53 พร้อมยอดที่ล็อกไว้ตอนจ่าย และหลักฐาน |

หลักฐานทุกชิ้น (สลิปโอน ใบกำกับภาษีของผู้ขาย หนังสือรับรองหัก ณ ที่จ่าย ใบเสร็จสรรพากร)
ใช้ตาราง `files` กลางที่มีอยู่แล้ว ซึ่งผูกกับระเบียนประเภทไหนก็ได้ (`owner_type`, `owner_id`)
เพิ่มแค่ค่า `owner_type` ใหม่ (`payment`, `expense`, `tax_filing`) ไฟล์อยู่บน R2 แบบ private เหมือนเดิม

**ยอดเงินเก็บเป็นค่าที่คำนวณแล้ว ไม่คำนวณใหม่ตอนอ่าน** เพราะเอกสารภาษีต้องแสดงสิ่งที่พิมพ์ออกไป
ตลอดไป ต่อให้อัตรา VAT หรือราคาตั้งต้นเปลี่ยนทีหลัง

## เลขที่เอกสาร

รูปแบบ `QO-2611-001` = ประเภท-ปีเดือน-ลำดับ ตั้งค่าได้ว่ารีเซ็ตรายเดือนหรือรายปี

กติกา 4 ข้อที่ห้ามพลาด:

1. **จองเลขตอนกด "ออกเอกสาร" ไม่ใช่ตอนสร้างร่าง** ร่างที่ทิ้งไว้จะได้ไม่กินเลข
2. **จองใน transaction เดียวกับการบันทึก** ด้วย `UPDATE document_counters SET next_value = next_value + 1 ... RETURNING next_value` แถวนั้นถูกล็อกระหว่าง transaction สองคนกดพร้อมกันจึงชนกันไม่ได้
3. **ยกเลิกแล้วเลขยังอยู่** ติดป้ายยกเลิกไว้ ไม่ลบ ไม่เอาเลขกลับมาใช้ซ้ำ — ใบกำกับภาษีมีเลขหายไม่ได้
4. **เอกสารที่ออกแล้วแก้ไม่ได้** ต้องยกเลิกแล้วออกใหม่ ก่อนออกเลขแก้ได้อิสระ

ต้องมีเทสต์ที่ยิงขอเลขพร้อมกันหลาย goroutine แล้วยืนยันว่าไม่มีเลขซ้ำและไม่มีเลขข้าม

## สถานะและสายเอกสาร

```
ร่าง ──ออกเอกสาร──► ออกแล้ว ──ยกเลิก──► ยกเลิกแล้ว
                        │
ใบเสนอราคา ──สร้างต่อ──► ใบแจ้งหนี้ ──สร้างต่อ──► ใบเสร็จ/ใบกำกับภาษี
```

"สร้างต่อ" ลอกลูกค้า รายการ และโหมดภาษีมาให้ แล้วเก็บ `source_document_id` ไว้
จึงย้อนดูได้ว่าใบเสร็จใบนี้มาจากใบเสนอราคาใบไหน

## รายรับ

ใบแจ้งหนี้หนึ่งใบรับเงินได้หลายครั้ง (มัดจำ งวด) แต่ละครั้งเป็นแถวใน `payments`

| ช่อง | หมายเหตุ |
| --- | --- |
| วันที่ได้รับ · ยอดที่โอนเข้าจริง | |
| ยอดที่ลูกค้าหัก ณ ที่จ่าย · อัตรา | ปกติงานบริการ 3% ของยอดก่อน VAT ระบบเสนอให้ แก้ได้ |
| สลิป/หลักฐานการรับเงิน | แนบตอนกด "ได้รับเงินแล้ว" |
| หนังสือรับรองหัก ณ ที่จ่าย (50 ทวิ) | สถานะ `รอ` → `ได้รับแล้ว` กดพร้อมแนบไฟล์ |

ยอดที่โอนเข้า + ยอดที่ถูกหัก = ยอดที่เก็บได้ของใบนั้น ระบบจึงรู้ว่าใบไหนจ่ายครบ ใบไหนค้าง

**หนังสือรับรองที่ยังไม่ได้คืนมาคือเงิน** เพราะยอดที่ถูกหักใช้เป็นเครดิตภาษีเงินได้ตอนสิ้นปีได้
ก็ต่อเมื่อมีหนังสือรับรอง จึงมีรายการ "รอหนังสือรับรองจากลูกค้า" แยกให้เห็น พร้อมยอดรวม

**ภาษีขายของงานบริการเกิดเมื่อได้รับเงิน** ใบเสร็จ/ใบกำกับภาษีจึงออกตอนบันทึกรับเงิน
และ VAT ของเดือนนับจากใบกำกับภาษีที่ออกในเดือนนั้น (ตรวจกับนักบัญชีอีกครั้ง ดู "ต้องรู้จากบริษัท")

## รายจ่าย

หนึ่งแถวใน `expenses` ต่อบิลของผู้ขาย

| ช่อง | หมายเหตุ |
| --- | --- |
| ผู้ขาย (`vendors`) · หมวด · รายละเอียด · ผูกกับลูกค้า/งานได้ (`lead_id`, null ได้) | ผูกงานได้ เพื่อดูต้นทุนต่องาน |
| เลขที่และวันที่ใบกำกับภาษีของผู้ขาย | |
| ยอดก่อน VAT · VAT (ภาษีซื้อ) | |
| มีใบกำกับภาษีเต็มรูปหรือไม่ · ไฟล์ใบกำกับ | **ไม่มีใบกำกับ = ภาษีซื้อเอามาหักไม่ได้** ระบบไม่นับยอดนี้เข้าภาษีซื้อ |
| เราหัก ณ ที่จ่ายหรือไม่ · อัตรา · ยอด | 1% ขนส่ง · 2% โฆษณา · 3% บริการ/จ้างทำของ · 5% ค่าเช่า (เลือกได้ แก้ได้) |
| แบบที่ต้องยื่น | ภ.ง.ด.3 ถ้าผู้รับเป็นบุคคล · ภ.ง.ด.53 ถ้าเป็นนิติบุคคล — มาจาก `vendors` |
| จ่ายแล้วหรือยัง | กด "จ่ายแล้ว" พร้อมแนบสลิป · ยอดที่โอน = ยอดรวม − ยอดที่หัก |
| ส่งหนังสือรับรองให้ผู้รับเงินแล้วหรือยัง | กด "ส่งแล้ว" พร้อมแนบสำเนา 50 ทวิ |

ภาษีซื้อเอามาหักในเดือนที่ได้ใบกำกับภาษี และกฎหมายให้ใช้ย้อนหลังได้ไม่เกิน 6 เดือน
ระบบเก็บ "เดือนที่ใช้ขอคืน" ไว้ในแถว ค่าตั้งต้นคือเดือนของใบกำกับ และเตือนใบที่ใกล้ครบ 6 เดือนแต่ยังไม่ได้ใช้

## ภาษีรายเดือน (`tax_filings`)

หนึ่งแถวต่อ (แบบ, งวด) ระบบคำนวณยอดจากเอกสาร คนกด "จ่ายแล้ว" พร้อมแนบใบเสร็จของสรรพากร

| แบบ | ยอด | กำหนดตามปกติ |
| --- | --- | --- |
| ภ.พ.30 | ภาษีขาย − ภาษีซื้อ ของเดือน ถ้าติดลบคือเครดิตยกไปเดือนหน้า | วันที่ 15 ของเดือนถัดไป (ยื่นออนไลน์ได้ช้ากว่า) |
| ภ.ง.ด.53 | ยอดที่เราหักนิติบุคคลในเดือน | วันที่ 7 ของเดือนถัดไป (ยื่นออนไลน์ได้ช้ากว่า) |
| ภ.ง.ด.3 | ยอดที่เราหักบุคคลธรรมดาในเดือน | วันที่ 7 ของเดือนถัดไป (ยื่นออนไลน์ได้ช้ากว่า) |

กติกา:

1. **ยอดที่จ่ายถูกล็อกไว้ในแถว** ตอนกด "จ่ายแล้ว" ถ้ามีคนแก้รายจ่ายหรือยกเลิกเอกสารของงวดนั้นทีหลัง
   ระบบไม่เปลี่ยนตัวเลขที่จ่ายไปแล้ว แต่ขึ้นป้าย "ยอดคำนวณใหม่ไม่ตรงกับที่ยื่น" ให้นักบัญชีดู
   (อาจต้องยื่นเพิ่มเติม) — ไม่แก้ย้อนหลังเงียบ ๆ
2. **งวดที่จ่ายแล้วแก้รายการในงวดไม่ได้โดยไม่ตั้งใจ** ต้องกดยืนยันและลง log ว่าใครแก้
3. **กำหนดยื่นขึ้นในปฏิทินกลางและหน้า "วันนี้" ของแอดมิน** ตั้งแต่ 5 วันก่อนครบ
4. ระบบไม่ยื่นแบบและไม่จ่ายภาษีเอง นักบัญชีหรือแอดมินยื่นที่เว็บสรรพากร แล้วกลับมากด "จ่ายแล้ว"

ตัวเลข "ยื่นออนไลน์ได้ช้ากว่า" ไม่ใส่วันตายตัวในโค้ด เพราะกรมสรรพากรขยายเป็นรอบ ๆ
เก็บเป็นค่าตั้งค่าในหน้าแอดมิน

## Dashboard รายรับ-รายจ่าย

อ่านจากเอกสาร **ไม่ใช่จาก `deals`** เพราะ `deals` คือยอดที่เซลส์ปิดได้ (มุมมองการขาย)
ส่วนเอกสารคือเงินจริง ทั้งสองอยู่ด้วยกันได้ และลิงก์กันผ่าน `lead_id` ถ้าต้องการ

ต่อเดือน:

| รายรับ | รายจ่าย | ภาษี |
| --- | --- | --- |
| ออกบิลแล้ว | รายจ่ายทั้งหมด | ภาษีขาย |
| เก็บเงินได้ (โอนเข้า + ถูกหัก) | จ่ายแล้ว / ค้างจ่าย | ภาษีซื้อที่ใช้ได้ |
| **ค้างรับ และเกินกำหนดกี่ใบ** | ภาษีซื้อที่ใช้ไม่ได้ (ไม่มีใบกำกับ) | **VAT ต้องจ่าย หรือเครดิตยกไป** · จ่ายแล้วหรือยัง |
| ถูกหัก ณ ที่จ่าย · **รอหนังสือรับรองกี่ใบ เท่าไหร่** | เราหัก ณ ที่จ่าย · **ส่งหนังสือรับรองแล้วหรือยัง** | ภ.ง.ด.3 / 53 ต้องนำส่ง · นำส่งแล้วหรือยัง |

แยกตามบริการ แยกตามลูกค้า และกำไรขั้นต้นต่องาน (รายรับของลูกค้า − รายจ่ายที่ผูกกับลูกค้านั้น)

**รายการที่ต้องตาม** อยู่บนสุดของหน้า: ใบแจ้งหนี้เกินกำหนด · หนังสือรับรองที่ลูกค้ายังไม่ส่ง ·
หนังสือรับรองที่เรายังไม่ส่งให้ผู้รับจ้าง · รายจ่ายที่ยังไม่มีใบกำกับภาษี · ภาษีที่ใกล้ครบกำหนด

## สิทธิ์

เซลส์ออกใบเสนอราคาและใบแจ้งหนี้ให้ลูกค้าของตัวเองได้ และเห็นสถานะการรับเงินของลูกค้าตัวเอง
รายจ่าย ภาษี และ Dashboard การเงินทั้งหมด **เฉพาะแอดมิน**

## ไม่ทำ

บัญชีคู่ ผังบัญชี งบทดลอง สมุดรายวัน เงินเดือนและประกันสังคม ภาษีเงินได้นิติบุคคลสิ้นปี
**การยื่นแบบหรือจ่ายภาษีแทนคน** (ระบบคำนวณและเก็บหลักฐาน คนยื่นเอง) และส่ง e-Tax Invoice
เข้าสรรพากร — นักบัญชียังทำหน้าที่เดิม ระบบทำให้เขาได้ตัวเลขกับหลักฐานครบในที่เดียว
มีปุ่ม export รายเดือน (รายงานภาษีขาย รายงานภาษีซื้อ รายการหัก ณ ที่จ่าย + ไฟล์หลักฐานเป็น zip)
ให้นักบัญชี และควรให้เขาตรวจเทมเพลตใบกำกับภาษีกับสูตร VAT/หัก ณ ที่จ่าย หนึ่งรอบก่อนใช้จริง

## การตัดสินใจจากบริษัท (16 พ.ย. 2026)

1. **อีเมลเป็นปุ่มร่าง** คนส่งเองข้างนอก ระบบไม่ส่ง
2. **บริษัทจด VAT และออกใบกำกับภาษีได้** ค่าตั้งต้น VAT แยก 7% สำนักงานใหญ่ ตาม owl-docs
3. **ต้องมีรายรับ** ได้เท่าไหร่ VAT รอจ่ายเท่าไหร่ ถูกหัก ณ ที่จ่ายเท่าไหร่ ปุ่มจ่ายแล้ว/ได้รับแล้วพร้อมแนบหลักฐาน
4. **ต้องมีรายจ่าย** VAT เท่าไหร่ หักลบกับภาษีขายแล้วเหลือจ่ายเท่าไหร่ หัก ณ ที่จ่ายนำส่งหรือยัง
   ส่งหนังสือรับรองให้อีกฝ่ายหรือยัง และหนังสือรับรองที่ลูกค้าต้องส่งให้เรา ได้รับหรือยัง

# แผน 5: เชื่อม owldayhouse.com เข้ากับ CRM — ระยะ 1

สถานะ: **ร่าง รอตัดสินใจ 2 ข้อก่อนเริ่ม** (ดูหัวข้อสุดท้าย)

ระยะ 1 ทำแค่ 3 อย่าง: รับบรีฟงานจากเว็บ เก็บที่มาของลูกค้า และมีหน้านโยบายความเป็นส่วนตัว
ส่วนที่เหลือ (นัดคุย ไฟล์แนบ ลิงก์ติดตามสถานะ รับสมัครงาน พอร์ทัลรายงาน) อยู่ในระยะถัดไป

## หลักการที่ห้ามพัง

เว็บการตลาดยังเป็น static 100% `output: 'export'` ขึ้น FTP เหมือนเดิม ไม่มี runtime ของตัวเอง
ฟอร์มเป็นแค่ HTML + `fetch()` ไปที่ **origin อื่น** พื้นที่เสี่ยงที่เพิ่มขึ้นคือ endpoint เดียว ไม่ใช่ทั้งเว็บ

```
owldayhouse.com  ──POST──►  api.owldayhouse.com  ──►  inbound_requests
(static, FTP)               (ประตูเดียว เขียนอย่างเดียว)        │ แอดมินกดรับ
                                                          ▼
                            crm.owldayhouse.com  ──────►  leads
                            (JWT ไม่เปิดให้ public แตะ)
```

**ประตูรับไม่เขียนลงตาราง `leads` โดยตรง** มันลงตารางพักที่ public มีสิทธิ์ `INSERT` อย่างเดียว
ไม่มี `SELECT` ไม่มี `UPDATE` ผลคือสแปมที่หลุดเข้ามาทำได้มากสุดคือทำให้กล่องขารับรก
ไม่ปนเข้า pipeline และไม่เห็นข้อมูลลูกค้าเจ้าอื่นแม้แต่แถวเดียว

## 1. ฟอร์ม

วางคู่กับปุ่ม Messenger/LINE/โทร **ไม่ใช่แทน** คนไทยจำนวนมากจะไม่กรอกฟอร์ม
ค่าที่เลือกได้ต้องตรงกับ enum ใน `apps/api/pkg/models/lead.go` ตั้งแต่วันแรก จะได้ไม่ต้องแปลงทีหลัง

| ขั้น | ถาม | ลงฟิลด์ |
| --- | --- | --- |
| 1 | สนใจบริการไหน (เลือกได้หลายอัน) | `interests[]` — ตรงกับ `Interest*` 6 ค่า |
| 2 | เล่างาน · ช่วงเวลาที่อยากได้ · ช่วงงบ | `brief`, `timeline`, `budget_band` |
| 3 | ชื่อ · บริษัท · กลุ่มธุรกิจ · ช่องทางติดต่อ | `contact_name`, `company`, `industry`, `phone`/`line_id`/`email` |

- ช่วงงบเป็น "ช่วง" ที่ลูกค้าบอกเอง ไม่ใช่ราคาที่เราแสดง — ไม่ขัดกฎ "เว็บไม่มีราคา"
- ไม่มีช่องไหนบังคับเกินจำเป็น ขอชื่อกับช่องทางติดต่อ 1 ช่องก็พอ

## 2. ที่มา

เก็บ `utm_source`, `utm_campaign`, `referrer`, `landing_path` (หน้าที่กดเข้าฟอร์ม)
`leads` มี `utm_source`/`utm_campaign` อยู่แล้ว เติมต่อได้เลยตอนกดรับ
ไม่ใช้คุกกี้ติดตาม — อ่านจาก query string กับ `document.referrer` เท่านั้น

## 3. PDPA — ต้องขึ้นก่อนหรือพร้อมฟอร์ม ไม่ใช่ตามหลัง

วันที่เริ่มเก็บชื่อ-เบอร์ผ่านฟอร์ม เราเป็นผู้ควบคุมข้อมูลส่วนบุคคลทันที ต้องมีครบ 4 อย่าง

1. หน้านโยบายความเป็นส่วนตัว (ตอนนี้ยังไม่มีใน `apps/web/app`)
2. checkbox ยินยอมที่ **ไม่ติ๊กมาให้** พร้อมลิงก์ไปหน้านโยบาย
3. ระยะเก็บข้อมูลที่ระบุชัด — เสนอ: คำขอที่ไม่ได้กดรับ ลบอัตโนมัติใน 180 วัน
4. ช่องทางขอลบ — ใช้ Messenger/อีเมลที่มีอยู่ บวกขั้นตอนภายในว่าใครลบและลบอย่างไร

เรื่องนี้ขายของให้เราด้วย เพราะเราเขียนบทความเก็บข้อมูลลูกค้าหน้าบูธแบบถูก PDPA ไว้เอง

## 4. ประตูรับ (`apps/api`)

### ตาราง `inbound_requests`

| คอลัมน์ | หมายเหตุ |
| --- | --- |
| `id`, `created_at` | |
| `kind` | `quote` วันนี้ เผื่อ `careers` ในระยะถัดไป |
| `interests`, `brief`, `timeline`, `budget_band` | จากฟอร์ม |
| `contact_name`, `company`, `industry`, `phone`, `line_id`, `email` | จากฟอร์ม |
| `utm_source`, `utm_campaign`, `referrer`, `landing_path`, `locale` | ที่มา |
| `ip_hash`, `user_agent` | ดูสแปมย้อนหลังโดยไม่เก็บ IP ตรง ๆ |
| `status` | `new` / `accepted` / `discarded` |
| `lead_id` | เติมตอนกดรับ |

### Routes

| Method | Path | ใคร |
| --- | --- | --- |
| `POST` | `/intake/quote` | public — ไม่มี auth ไม่มี GET |
| `GET` | `/api/inbox` | admin + sales |
| `POST` | `/api/inbox/:id/accept` | สร้าง lead `source=website` แล้วผูก `lead_id` |
| `POST` | `/api/inbox/:id/discard` | พร้อมเหตุผลสั้น ๆ |

ตอนกดรับให้เรียกตัวตรวจชื่อซ้ำที่มีอยู่ (`GET /api/leads/check`, pg_trgm) ก่อน
จะได้ไม่สร้างลูกค้าซ้ำกับที่เซลส์ลงไว้แล้ว

### แยกให้ขาด

- **คนละ origin** `api.owldayhouse.com` กับ `crm.owldayhouse.com` คนละ site block ใน Caddy
- **คนละ process** คนละ container
- **คนละ Postgres role** role ของประตูรับ `INSERT` ลง `inbound_requests` ได้อย่างเดียว

## 5. กล่องงานเข้าใน CRM

เครื่องมือใหม่ `/inbox` — ตอนนี้ราคาถูกแล้ว เพราะ `apps/internal` มี shadcn เป็นฐาน
และ `lib/tools.ts` เป็นที่เดียวที่ต้องเติม (เมนู แถบล่างบนมือถือ breadcrumb และหน้ารวมตามให้เอง)

หน้าจอ: รายการคำขอใหม่ → กดดูรายละเอียด → "รับเข้าระบบ" (เลือกเจ้าของ) หรือ "ทิ้ง"
ทุก action ใส่ `meta: { success: "…" }` ตามแบบที่วางไว้แล้ว

**แจ้งเตือน: ไม่มีอีเมล** ระยะ 1 ใช้ตัวเลขบนเมนูกับหน้า "วันนี้" ก่อน
ถ้าต้องการเตือนเข้ามือถือจริง ๆ ค่อยต่อ LINE Messaging API ในระยะถัดไป

## 6. ความปลอดภัยขั้นต่ำของระยะ 1

ข้อ 1-4 ต้องมีตั้งแต่วันแรก

1. ประตูรับ **เขียนได้อย่างเดียว ไม่มี GET ไม่มี auth ไม่มี admin surface** — ไม่มี login ก็ไม่มีรหัสให้เดา
2. Turnstile (Cloudflare) + honeypot + rate limit ต่อ IP และทั้งระบบ + ปฏิเสธฟอร์มที่กรอกเสร็จใน < 3 วินาที
3. body limit **16KB** ไม่ใช่ 25M ที่ CRM ใช้ และ validate แบบ allowlist ทุก enum จำกัดความยาวทุกฟิลด์
4. ไม่มี secret ใน bundle ของเว็บ static นอกจาก Turnstile site key กับ URL ของประตู
5. **CSV injection** — `ExportLeads` มีอยู่แล้ว ข้อความจากเว็บที่ขึ้นต้นด้วย `=` `+` `-` `@` จะกลายเป็นสูตรใน Excel ของเราเอง ต้อง escape ตอน export
6. ถ้าเอา Cloudflare มาคร่อม: `infra/digitalocean/Caddyfile` เตือนไว้แล้วว่า orange cloud ทำให้ HTTP-01 พัง ต้องเปลี่ยน image เป็นตัวที่มี Cloudflare DNS plugin **ก่อน** ไม่ใช่เปิดแล้วค่อยแก้
7. UFW เปิดแค่ 80/443/22 · Postgres ไม่ publish port · fail2ban · unattended-upgrades
8. ขยาย `OwnershipLog` ให้บันทึกว่าใครกดรับคำขอไหนเป็น lead

## สองเรื่องที่ต้องตัดสินใจก่อนเริ่ม

**1. CLAUDE.md กับ README ห้ามฟอร์มไว้ตรง ๆ**

- CLAUDE.md: *"Marketing site = 100% static. No backend, no email, no forms."*
- `docs/design-system/project/README.md`: *"ห้ามทำฟอร์มบนเว็บการตลาด เว็บเป็น static ทั้งหมด"*

เจตนาของกฎคือ "เว็บต้องไม่มี runtime ของตัวเอง" ซึ่งแผนนี้ยังรักษาไว้ครบ
แต่ตัวหนังสือห้าม forms ชัดเจน ถ้าจะทำต้องแก้ข้อความทั้งสองที่ให้เป็น
"ฟอร์มได้ แต่ยิงออกไป origin ภายนอกเท่านั้น ห้าม runtime ในเว็บ" ไม่ใช่ทำเงียบ ๆ
แล้วปล่อยให้เอกสารขัดกับโค้ด

**2. ไม่มีอีเมลในระบบนี้**

ฟอร์มเก็บอีเมลลูกค้าเป็น "ข้อมูล" ได้ (CLAUDE.md อนุญาตไว้) แต่ระบบยังส่งอีเมลไม่ได้
แปลว่าคนกรอกฟอร์มจะ **ไม่ได้รับอีเมลยืนยัน** ต้องยอมรับข้อนี้ และต้องเขียนบนหน้าฟอร์มให้ชัด
ว่าเราจะติดต่อกลับทางช่องทางที่เขาให้ไว้ภายในกี่วันทำการ
